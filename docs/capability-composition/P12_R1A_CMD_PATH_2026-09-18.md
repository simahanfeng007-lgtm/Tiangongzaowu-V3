## Bounded correction in the existing SandboxRunner

After the existing workspace copy, link checks and real-to-private path rebinding,
`_prepare_windows_cmd_initial_directory` handles only a raw command string invoking
the exact system CMD, with unambiguous /c and optional /d and /s switches, and an
INITIAL literal quoted cd/chdir. Both cwd and target must be ordinary drive-absolute
paths within the same existing private workspace. The target becomes relpath(target,
cwd); operation, switches, command suffix and launch cwd stay unchanged.

For this initial command, process cwd is known and no user command has run yet,
so the relative target identifies the same private directory. It avoids asking
CMD to canonicalize the whole host-profile ancestry. The translation does not use
`cd` movement as new execution authority and does not open a second workspace.

Ambiguous flags, custom shells, argv-list forms, subsequent cd statements,
expansions/metacharacters in the target, redirects attached to cd, UNC/extended
paths and targets outside the private workspace remain byte-for-byte unchanged.
This is deliberately NOT a general CMD interpreter or a claim that every absolute
path operation in every shell is now supported. A rejected/unknown translation is
not executed by a weaker fallback; the existing native policy still applies.

No ACL, environment allowlist, native launcher, AppContainer capability, timeout,
process limit, A5 rule, Source authority, registry, store schema, CompletionGate,
Golden corpus or independent fingerprint is changed. Existing PowerShell support
and all original foundation tests remain intact. Parent ACLs are not widened.
