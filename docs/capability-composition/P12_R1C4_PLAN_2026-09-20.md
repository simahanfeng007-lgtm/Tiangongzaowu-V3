编制：2026-09-20。基线：main `069d258`（含 R1C3，PR #79）。
性质：本批工作包的实施计划与反例矩阵映射；实现随本文件同批交付。

## 一、目标与边界

把 R1C3 已登记/封存的 `SourceCompositionResult` 计划，经**原** Adapter（CompositionActivationAdapter）、Policy/Ticket/Grant（OmniGrantAuthority）、步骤授权（CompositionStepAuthorizationRequest/Artifacts）、Runtime（CompositionStepExecutionCoordinator + backend 通道）执行，落 Effect/Fact，由原 P19（VerificationPlanExecutor/Readiness）验证，最终由原 CompletionGate 判定——一个 A0 read/verify 小任务的完整受控往返。

- 不新增第二调度/状态机/Runtime/授权链；全部经现有入口。
- 登记≠执行、动作成功≠业务完成：最终判定权在 CompletionGate。
- backend 响应用确定性 in-process 夹具（沿用 P7D1 范式），测试文件头明确标注证据边界：这是链路/状态机证据，不是真实模型/真实施工验收（那属 R1G/D03）。
- AMBIGUOUS 先对账不重放；当前 A0 范围内无外发/删除类副作用。

## 二、现状（已核实）

- 登记段（R1C3）：`register_production_composition` → store 复合入口（P19 权威+P7B.1 登记+executable 封存+P9 保留）已在 main，12 项集成/反例测试绿。
- 执行段（P7D1）：`CompositionStepExecutionCoordinator.dispatch_record` 经 `GatewayOrchestrationWorker` 组装（orchestration.py:547），对已登记 plan 的授权→Effect→Fact→terminal 状态机已有完整测试（真 Store/FactLedger + `_BackendProbe` 夹具响应）。
- 授权段（P7C1）：`OmniGrantAuthority` + parent ticket + `CompositionStepAuthorizationRequest` 物化（含 materialized_arguments/target/object grants）已有对抗测试。
- **缺口**：三段从未在同一次运行里以「R1C2 真实来源 → R1C3 intake 登记 → 原执行链 → P19 → Completion」连成一条链；R1C3 fixture 世界的执行权威件（signer/trust/schema catalog/parent ticket/coordinator）尚未搭建。

## 六、结果记录（2026-09-20，本批第 1 次提交）

- `tests/test_source_execution_roundtrip_p12.py` 3 项全绿（真实组件）：
  1. 正向主链：R1C3 登记 → `issue_composition_step`（原 Policy/Ticket/Grant）→ `dispatch_record`（原协调器）→ backend（确定性夹具，文件头已标注证据边界）→ Effect SUCCEEDED + Fact batch 落账；登记自身零 Effect。
  2. 重复 dispatch 幂等：同授权只执行一次，Effect 计数不变。
  3. 代际释放拒绝：release 后 Store 拒绝发放步骤授权（零副作用）。
- 生产代码零改动：登记→执行链路完全由既有权威承担（这正是 R1C4 要证明的事）。
- 实现中发现并遵守的原合同细节：v1 静态根步不支持 object 参数（object_grant_only 资源政策的参数须为 object id 或无参）；父效应须先有已验证 Fact batch；协调器实例 id 须与代际租约 owner 一致；backend 响应受 result schema 严格校验。
- 同包待补（下一提交，不阻塞本批）：CompletionGate 终局判定两例（验证通过→完成、缺验证→不完成）、AMBIGUOUS 对账恢复、重启恢复。
