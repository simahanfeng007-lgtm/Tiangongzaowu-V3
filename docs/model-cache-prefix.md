普通字典执行循环的真实 DeepSeek 输入缓存命中率原来只有约 5%。每轮最新世界状态的 `packet_id`、查询标识和时间戳位于 system 提示中段，导致后面的固定协议、任务与历史无法复用；组合工具回执还会重复进入旧观察和原生历史，原生历史在 96,000 字符处过早移出。

## 请求布局

运行时现在按“固定 system/工具协议 → 初始任务种子 → 已验证的原生调用与结果 → 宿主观察、当前反馈 → 最新世界状态”排列。初始种子保留启动快照；末尾明确标记本轮最新状态，每轮重新获取，不改写任何来源标识、签名或时间。状态文本明确属于非授权数据。完整 WU 标记块才移位，不完整标记保持原样。

Chat Completions、Responses、Anthropic 共用布局入口。原生 call/result ID、原始结果和协议续答状态不变；跨模型或 provider 失配时保留旧观察回退。只有运行时显式启用新布局，旧单轮适配接口保持兼容。

去重必须逐字匹配已验证的原生结果，或显式 `tiangong.task-composition-result.v1` 的叶子结果。完整结果仍在原生对中；宿主失败、缺口、提示、质检建议和对抗反馈继续独立保留。任意嵌套文本或同名动作不足以触发去重。

原生历史按估算 token 预算保留，不再按固定字符数裁剪：预算为 `min(96000, 60% × DEFAULT_WINDOW_TOKENS - 固定提示估算)`，下限 1；超预算或超过 32 组时整组移出，目标为预算的 75% 且至多 24 组，至少保留最新一组。移出数量明确提示模型，缺失内容需要重新读取。估算包括私有续答状态，但不将其写入日志。这沿用既有配置窗口，并不新增按服务端实际窗口自动探测，也不保证单个超大结果不会溢出。

统计补齐 DeepSeek 的 `prompt_cache_hit_tokens` 字段，并以实际出站协议记录固定前缀摘要。[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/kv_cache/)解释了前缀缓存和 hit/miss 计数；缓存由服务端尽力保留，不保证每轮命中。

中间候选文件/代码命中率为 28.86% / 64.81%，其运行原样保留；文件历史仍被旧字符上限裁剪，随后才补上 token 预算修复。最终两组历史均未发生移出，system 和初始种子摘要逐轮一致，最新 WU 摘要仍变化。两组均正常关闭，数据库只读审计前后哈希一致。

这是两种任务的本机试验，模型规划和调用数会变化，且服务端缓存可能交叉预热，不是随机化性能基准，不据此承诺所有任务同等收益或将耗时差异全部归于缓存。
