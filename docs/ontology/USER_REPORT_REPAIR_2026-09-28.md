# 用户反馈：首启等待与模型 HTTP 失败

基线为 2026-09-27 已合入的 main `f43e2f25338f80a0216bd459780090fda629d134`。反馈截图描述两件事：从仓库安装后长时间只见启动画面，以及任务在出现 `http_error` 时把是否继续交给用户。截图没有 HTTP 状态、客户端日志或用户机器信息，因此不能据此断定对方的具体接口故障原因。

## 修复与边界

- **启动：**原 `createWindow` 在加载正式前端前等待 `serviceSupervisor.startAll()`；源码模式的网关健康等待可持续 600 秒。前端启动读取模型设置还会在连接失败时再次等待该服务。现在先加载桌面，再由原服务管理器后台启动和广播状态；启动读取快速返回离线，用户主动保存设置仍按原事务等待。窗口重建守卫避免旧异步结果作用于新窗口。只有网关 ready 且渲染器完成启动才提交更新健康标记。
- **模型失败：**可恢复的 HTTP 408/425/429/5xx 在原模型调用边界内按时限最多尝试三次；401/402/409 不盲目重试。`Retry-After` 不越过本轮截止。失败回执保留安全的 HTTP 状态和重试次数；界面给出具体中文原因，不显示裸 `http_error`，不把未完成任务判成完成，也不要求为原已授权任务重新确认。持久服务故障仍会停止本轮，保留实际进度，待连接恢复后从事实记录继续；已执行的工具副作用不随模型请求重放。
- **安装检查：**两份 Windows 首次运行 QA 脚本改为读取按日期轮转的桌面诊断日志，并覆盖跨日文件；此前固定文件名会导致误报无日志。
